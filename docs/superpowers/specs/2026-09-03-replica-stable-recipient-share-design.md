# Replica-Stable Recipient Share Design

## Goal

Make a `/show/<shared>/<recipient>` or `/query/<shared>/<recipient>` URL generated by the primary node resolve on every read-only replica, even when each node uses an independent `SECRET_KEY`.

## Current Failure

The `shared` path segment is currently recomputed as an HMAC of `account_id` with the local Flask `SECRET_KEY`. Replica deployments intentionally use independent keys, so a replica computes a different segment and returns `404` before checking replica readiness.

## Design

Add `accounts.recipient_share_segment`, a non-secret opaque base64url value shared by every recipient link owned by that account.

- Existing primary databases backfill the column with the current HMAC-derived value. Existing primary-generated URLs therefore remain valid.
- New accounts receive a random 32-byte base64url segment when their first recipient link is created.
- URL generation reads the persisted account value.
- Public route resolution compares the incoming segment with the persisted account value and never recomputes it from the local node key.
- The account snapshot and increment payloads carry the field to replicas.

The legacy `/api/v2/mailboxes/<token>` route and per-recipient token hashes remain unchanged.

## Upgrade And Replication

The cluster protocol version increases because the exact account payload shape changes.

On primary startup, schema migration installs the new column and backfills accounts that already own recipient links. Backfill runs after replication triggers are installed, producing account upsert events.

On an existing replica, adding the column clears `last_success_at`. The sync worker therefore requests a full snapshot before the replica becomes ready, preventing a window where old local rows have an empty segment. A fresh replica already starts without a successful snapshot.

Mixed protocol versions fail closed through the existing protocol-version check until both nodes are upgraded.

## Validation And Security

Replicated segments must be base64url text between 32 and 128 characters. The value is an opaque bearer-like routing identifier and is never logged or returned by cluster status APIs.

Sharing the persisted segment does not expose either node's `SECRET_KEY`. Existing keys stay independent and locally encrypt sensitive account credentials as before.

## Tests

- Schema migration adds and backfills the account field without changing an existing public URL.
- New recipient links for one account reuse one persisted random segment.
- A primary snapshot applied to a replica with a different `SECRET_KEY` preserves the segment.
- The primary-generated `/show/` URL resolves on that replica.
- Snapshot and increment payload validation rejects malformed segments.
- Existing public token, expiry, readiness, and access-count behavior remains covered by the current suites.

## Scope

Only recipient mailbox public-link identity, database migration, cluster account payloads, and their tests change. No new dependency, UI change, or secret-sharing configuration is introduced.
